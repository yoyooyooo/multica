This generation assigns the fork reconciliation sequence new unique prefixes `231`–`243`. The SQL is intentionally additive/idempotent so both paths converge:

1. clean official v0.4.12 database: official `001`–`230`, then fork `231`–`243`;
2. deployed fork/v0.4.9 database: historical fork ledger retained, official v0.4.12 `224`–`230` applied by exact filename, then fork `231`–`243` reapplied as reconciliation;
3. retained historical-135 and fork/v0.4.8 fixtures: forward-converged through the same current sequence.

Migration `241_external_pr_index_reconciliation_fence` is forward-only. Rollback across it requires restoration of an accepted pre-v0.4.12 database backup rather than migration down.
